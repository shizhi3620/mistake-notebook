# 首版用户反馈最小闭环

**Status:** ready-for-agent

## Problem Statement

首版产品需要在 AI 单题讲解和主要功能投入真实使用后，获得可定位、可审计的用户反馈。当前需求已经要求讲解结果支持反馈，但尚未形成统一的反馈范围、关联关系、隐私边界和处理状态。缺少反馈会使题干识别、答案、讲解质量、功能可用性和未成年人内容安全问题无法进入持续改进闭环。

## Solution

首版提供轻量的用户反馈能力，分为单题讲解质量反馈、通用功能反馈和内容安全反馈三类。单题反馈必须绑定一次具体的单题讲解结果；功能反馈可从设置/帮助或首页提交；内容安全反馈单独进入高优先级审核队列。用户提交后只看到“反馈已收到”，内部保留可查询、可备注和可导出的处理状态。

## User Stories

1. 作为家长，我想对一次单题讲解标记“有帮助”或“有问题”，以便反馈结果是否满足学习需要。
2. 作为家长，我想指出题干、答案、讲解或难度中的具体问题，以便运营人员快速定位质量缺陷。
3. 作为家长，我想为质量反馈填写补充说明，以便解释自动分类无法表达的情况。
4. 作为家长，我想在讲解失败、低置信度或结果不适用时提交反馈，以便系统记录真实失败场景。
5. 作为家长，我想提交“功能不好用”“操作失败”“功能建议”或“其他”类型的通用反馈，以便反馈拍题、错题本、复习和提醒等产品体验。
6. 作为家长，我想从当前页面提交功能反馈，以便系统自动带上页面和版本上下文，减少重复描述。
7. 作为家长，我想举报不当、危险、歧视或不适合未成年人的内容，以便问题进入优先安全审核。
8. 作为家长，我想在提交后看到明确的收到确认，以便知道反馈没有丢失。
9. 作为家长，我不希望反馈表单要求上传新的图片或暴露个人信息，以便降低隐私风险。
10. 作为运营审核员，我想按反馈类型和处理状态查看反馈，以便分别处理质量问题、功能问题和安全问题。
11. 作为运营审核员，我想看到反馈关联的题目、孩子、讲解版本、模型版本和请求版本，以便复现问题并追踪影响范围。
12. 作为运营审核员，我想为反馈添加内部备注并标记处理结果，以便形成可审计的处理记录。
13. 作为发布负责人，我想统计反馈率、各类型数量和处理状态，以便评估首版质量和后续发布风险。
14. 作为数据管理员，我想让反馈只属于提交它的家长账户及其孩子档案，以便不同家庭之间严格隔离。
15. 作为合规负责人，我想让反馈内容遵守未成年人内容安全检测和数据最小化规则，以便反馈闭环不引入新的合规风险。

## Implementation Decisions

- 反馈能力通过 `LearningLoop` 公共反馈接口提供领域行为；HTTP API 仅负责认证、输入校验、错误映射和响应序列化。
- 反馈分为三类：`explanation_quality`、`feature`、`safety`。
- `explanation_quality` 必须关联一次具体的单题讲解结果，并记录题目、孩子档案、家长账户、讲解/模型/请求版本和提交时间。
- 质量反馈的结果为 `helpful` 或 `problematic`。`problematic` 可选择一个或多个问题项：`question_text`、`answer`、`explanation`、`difficulty`；说明文字可选，长度限制为 1–500 字。
- `feature` 不要求关联题目，但应记录提交页面、客户端版本和账户上下文。功能分类为 `usability`、`operation_failure`、`feature_request`、`other`；说明文字可选，长度限制为 1–500 字。
- `safety` 必须关联具体单题讲解结果；说明文字必填，长度限制为 1–500 字。该类型使用独立的高优先级处理队列和状态视图。
- 反馈初始状态为 `new`，内部状态流转为 `new`、`reviewing`、`resolved` 或 `rejected`。用户端不展示处理进度，不发送处理结果通知。
- 反馈记录不可静默改写其题目、讲解版本、模型版本和请求版本关联；内部备注和处理状态应保留变更审计信息。
- 所有读取和管理操作必须校验家长账户归属；运营审核仅暴露处理案件所需的最小数据。
- 首版不允许用户上传新的反馈附件；单题反馈可引用已有题目图片或讲解上下文，但提交界面必须提示不要填写姓名、学号、电话等个人信息。
- 反馈正文和说明纳入现有未成年人内容安全检测策略；检测失败时拒绝提交或转安全审核，不影响原学习流程。
- 反馈接口应支持幂等提交，重复请求不产生重复反馈；错误响应沿用现有 HTTP 错误结构。
- 观测指标至少包括反馈率、按类型的提交量、问题项分布、安全反馈量、处理时长和未处理数量；指标不得包含原始题干或个人敏感信息。

## Testing Decisions

- 最高层测试 seam 是 `LearningLoop` 公共反馈接口，验证创建、字段约束、账户/孩子归属、状态流转和幂等行为；测试只断言外部可见结果，不依赖存储实现细节。
- HTTP API seam 验证三类反馈的请求/响应契约、认证失败、越权访问、错误结构和重复 `Idempotency-Key` 请求。
- 单题讲解质量反馈测试覆盖：完整关联、问题项选择、说明长度边界、低置信度结果关联和版本追溯。
- 功能反馈测试覆盖：四种分类、页面与客户端版本上下文、无题目关联提交和账户隔离。
- 内容安全反馈测试覆盖：必须关联讲解结果、说明必填、高优先级队列标记和安全检测失败路径。
- 状态测试覆盖 `new` 到 `reviewing`、`resolved`、`rejected` 的合法流转，以及非法流转拒绝和内部备注审计。
- 幂等测试覆盖重复提交返回首次结果，不创建重复记录；并发竞争返回稳定结果。
- 隐私测试覆盖不接受新增附件、敏感信息提示/检测、跨账户不可读，以及管理端最小字段暴露。
- 测试风格沿用现有领域测试、HTTP seam 测试和 MySQL/SQLite 存储契约测试；新增持久化时补充真实异步存储 round-trip。

## Out of Scope

- 用户侧查看处理进度、处理结论或接收通知。
- 完整客服工单系统、人工申诉 SLA、自动回复和用户回访。
- 反馈附件上传、额外图片存储和图片编辑。
- 支付、订阅、退款或权益相关反馈流程。
- 面向其他用户公开反馈、评分、排行榜或社区讨论。
- 自动根据反馈修改模型、讲解内容、知识点或复习计划。
- 与本反馈需求无关的题目识别、讲解、错题本和复习规则改造。

## Further Notes

该规格落实现有 PRD 对讲解反馈、反馈率监控、未成年人内容安全和人工处理机制的要求。质量反馈与功能反馈共用领域入口但保持不同关联约束；安全反馈在数据模型和处理视图上保持独立。首版重点是可追溯收集和内部处理，不承诺即时修复或对用户公开处理结果。
